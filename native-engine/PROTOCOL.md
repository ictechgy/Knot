# Knot Native Engine v1 research contract

Status: experimental vertical slice; independent of Sunshine, Moonlight and Glimmer. Windows11 x64/Home logged-in SDR primary desktop host -> AppleSilicon macOS26+ viewer. No prelogin, lock/UAC secure desktop, audio, files, virtual monitor, updater, saved pairing or automatic reconnect in this first slice. Existing product remains unchanged for comparison.

## Short-code provisioning

Native.5 adds the separate bounded PAKE enrollment service in [ENROLLMENT.md](ENROLLMENT.md). Windows Share explicitly authorizes one code holder; authenticated enrollment mints a distinct one-use T2 with a30second media-claim deadline. Only a valid T2 claim on a NEW existing pinned TLS connection uses this preauthorization. The provisioning socket never carries media. Legacy runs retain the120second invitation and explicit approval below; switching modes creates a fresh run and revokes the prior slot/grant. No saved pairing or automatic reconnect is implied.

## Transport and trust

One full-duplex TLS/TCP connection, port48631 by default; TLS1.2 minimum, OS cryptographic libraries only. TCP is a deliberately simple proof transport, not a claim of Wi-Fi media optimization. Separate directions allow server video writes concurrently with client input writes. One sender and one reader per TLSstream. Strict bounded messages; stalled handshake/read/write ends the connection.

Host creates a fresh self-signed server-auth certificate for each sharing run (subject/SAN DNS `knot-native`, SHA256 over exact DER). Its validity interval is creation time minus24hours through plus24hours, to tolerate clock skew and independently verify the fresh exported public certificate across CI jobs. This does not extend the120second invitation or persist trust: exact pin, OS validity/server purpose/name, one-use token and run-specific authorization remain mandatory: explicit approval in legacy mode, or a valid one-use T2 claim after Windows sharing preauthorization in enrollment mode. No existing certificates, services, accounts, settings or preferences are adopted. Any OS key-container resources created by this run have random names and owned cleanup. No permanent peer state in v1.

Host explicitly clicks Share, creates 32random invite-token bytes with CSPRNG, valid120seconds. Invitation is `knot-native:v1:` followed by unpadded base64url UTF8 JSON with EXACT keys `v`, `address`, `port`, `certificateSHA256`, `token`. v=1; address canonical private IPv4 RFC1918 or Tailscale100.64/10 only; port1..65535; certificateSHA256=64lowercasehex; token=43base64url chars decoding to32bytes. Invitation max2048UTF8bytes, no URL lookups or implicit connection. It is a secret, shown/copied only on user action, never logged. Native invitation is separate from legacy address-only links. Viewer reviews target/pin and explicitly connects using exact DER pin; TLS proves possession. Verify certificate validity/server purpose with the pinned certificate as the sole anchor; expected DNSname `knot-native`. No accept-all callback, TOFU reset or silent fallback.

Client sends hello over authenticatedTLS, containing EXACT JSON keys v=1, token (same32bytebase64url), name (1..64UTF8bytes, no Unicode control/format characters or line/paragraph separators). Host rejects untrusted/public source IPv4, wrong/expired/reused token before any approval UI, capture or input. Constant-time comparison for equal-length decodedtoken. At most one pending invitation claim; atomic one-use claim before approval, userexplicitApprove within60seconds, reject/timeout consumes invitation. Sharing/capture begins only after valid run-specific authorization and media initialization. In legacy mode that authorization is explicit approval; in enrollment mode it is the later one-use T2 claim bound to the authenticated slot/run. Stop, close or disconnect releases all injected keys/buttons and destroys only owned resources. New connection requires a new invitation; no hidden saved trust or automatic reconnect. This temporary trust model is explicitly displayed by both apps.

Preclaim/enrollment deadlines use explicit completion-versus-expiry ownership. A queued timer callback cannot close a socket after successful completion wins. Completion checks the original monotonic budget independently of timer scheduling; backwards/late clocks fail closed and ordinary failure cleanup closes the connection.

Windows displays the exact current run's certificate pin for comparison with the reviewed Mac invitation. Approval displays the source IPv4 observed on the accepted socket and the viewer's claimed label; neither the label nor the address is an authenticated viewer identity. Invalid/preclaim connections cannot publish approval metadata. UI callbacks must belong to the displayed run.

Input revocation requests release of this session's owned input only. A failed `ReleaseAll` ends the connection before any later input is accepted, with up to three owned-release retry passes during teardown. Windows may refuse every attempt during a desktop transition; bounded cleanup is not proof of a successful OS release. Stop status reports the release request rather than claiming unverified success.

The viewer allows65seconds of read silence before Ready while waiting for approval or media initialization, with an overall125second stage deadline (60seconds approval, up to60seconds initialization and scheduling allowance). The host emits a heartbeat immediately before media initialization. After Ready the ordinary read/silence budget is10seconds and the first-presented-image budget is15seconds. These budgets bound viewer waiting; they do not make an in-process GPU/codec call preemptible. No new wire message or automatic reconnect is introduced.

## Binary frame envelope

Every message: u8kind + u32BEpayloadLength + exactly payloadLength bytes. Header5bytes. Unknown kinds, zero/oversize forbidden payloads, invalidUTF8/JSON, duplicate or extraJSON keys, out-of-order handshake and trailing data in typed packets fail closed. Never allocate from unchecked network lengths.

Client->host:
- 0x01 Hello: UTF8 JSON above, 1..4096bytes, first only; ten-second handshake/hello budget.
- 0x20 PhysicalKey: 4bytes = u8action(0up,1down), u16BEscanCode(1..255), u8extended(0/1). Max128retained pressed keys; no global hooks. ScanCodes are Windows set1.
- 0x21 Text: strict UTF8 1..1024bytes; committed text only, max512UTF16units; rejectNUL/invalidsurrogates. No arbitrary commands.
- 0x22 Pointer: 5bytes = u8action(0move,1leftdown,2leftup,3rightdown,4rightup,5middledown,6middleup), u16BEx,u16BEy. Coordinates normalized0..65535 over full captured rectangle; host maps to physical capturedmonitor then desktopvirtualscreen for SendInput.
- 0x23 Wheel: 8bytes = i32BEvertical,i32BEhorizontal, each -1200..1200.
- 0x24 ReleaseAll: empty, releases this session's accepted injected input only.
- 0x25 Heartbeat: empty, clientevery2s; ten-second inactivity timeout.

Server->client:
- 0x02 Ready: strict JSON exactkeys v=1, codec="h264-annexb", width,height (even,16..3840/2160; at most8_294_400pixels), fps(1..60), bitrate(1_000_000..40_000_000), hardwareEncoder=true. No ready before approved authenticated session + successful native media initialization.
- 0x03 Video: u64BEsequence(start1, strictlyincreasing), u64BEcaptureMonotonicMicroseconds(hostclock; NOT comparable to clientclock withoutsync), u8flags(bit0clean/IDR, otherbits0), then nonempty AnnexB H264 accessunit. Payload length18..4_194_304bytes excludes the5byte envelope; compressed data startsafter17payloadbytes and must independently pass AnnexB syntax validation. Every keyframe must provide parameter sets when available; decoder waits for validSPS/PPS+IDR. Reject malformed NAL structure/length; shared v1 limits are128NALs peraccessunit, atmost8SPS and8PPS, eachparameter NAL atmost65_536bytes. Enforce these onproducer/cacheprepend andbothconsumers, and validate decoded dimensions. No game/app launch, filesystem or shell messages.
- 0x04 Heartbeat: empty, hostevery2s evenifno desktop updates.
- 0x7f Error: strict JSON exactkey code, authored enum `auth`,`expired`,`declined`,`busy`,`capture`,`encoder`,`input`,`protocol`,`timeout`,`closed`; max128bytes. No rawexceptions, endpoints, credentials or OS strings.

All clientposthello packet sizes asabove and max1024. Serverready4096/error128/video4MiB caps. The client paces all input envelopes, including heartbeats, to at most500/s. The host uses a monotonic token bucket refilling500envelopes/s with capacity1000, permitting a bounded TCP delivery burst while rejecting sustained abuse. Pendingclientinput remains <=256actions/16KiB. Only consecutive trailing mouse moves may be coalesced: wheel, key, text and button actions are ordering barriers. Adjacent wheel coalescing must preserve both axes, payload bounds and those barriers. A physically forwarded key-down owns its matching key-up independently of later text-mode/modifier changes. On saturation, revoke unsent work, ReleaseAll or disconnect, require focus recovery; no stale input replay. Stop/read/write/decoder failure and focusloss trigger release; host tracks only successfully injected input.

Decoder admission suspends the sole reader when its three-slot capacity is full; capacity includes decoded images waiting for MainActor delivery. Stop/cancellation wakes admission waiters. A documented non-error dropped-frame completion retires its slot without ending the session. A malformed compressed unit or genuine decoder error still fails closed; arbitrary compressed reference frames are never dropped to hide queue pressure.

Video uses backpressure: capture/encode the next frame after previouswrite, no unbounded raw/encoded frame queue. The host requests a256KiB socket send buffer; write completion is not peer delivery and OS/TLS buffering is separate from application queue bounds. Codec lowlatency and periodic IDR, bounded operation waits; hardware encoder required in normal host. Software encoding is permitted only in clearly named fresh synthetic CI tests, never an implicit runtime fallback. SDR only; unsupportedHDR/rotation/device state fails with fixedguidance.

## Native Windows media ABI

Owned C++ DLL `KnotNativeMedia.dll`, C cdecl exports, fixedwidth types/pack4; create/read/close called on one dedicated MTA thread. Config uint32 width,height,fps,bitrate. Info uint32 width,height,fps,bitrate; int32 left,top,desktopWidth,desktopHeight; uint32 hardwareEncoder. `void* kn_media_create(const KnMediaConfig*,KnMediaInfo*,int32_t*error)`. `int32_t kn_media_read(void*,uint8_t*buffer,uint32_tcapacity,uint32_t*written,uint32_t*flags,uint64_t*timestampMicros)`. `void kn_media_close(void*)`. status0=sample,1=tryagain;-1generic,-2unsupporteddisplay,-3nohardwareencoder,-4devicefailure,-5invalidargument. Readbounded <=500ms and never writesbeyondcapacity. Native media headers are authoritative for actual struct names; coordinate/ABI edits require notifying otherworker. Syntheticmedia tests use a separate test entry, not any remoteflag.

## Native.6 latency policy

The client explicitly disables Nagle aggregation for small input envelopes. Input is selected after its existing pacing wait so the latest consecutive move remains eligible; the500/s limit, action barriers, revocation epochs and sole writer are unchanged.

A single serial media reader actor owns framed reads, stream-order validation, Annex B parsing and one-time AVCC construction. It prepares at most one next unit while the existing MainActor decoder submission and three-ticket admission apply backpressure. It creates no per-frame tasks and does not drop compressed predictive frames. UI/input and stop/revocation can progress while media preparation runs; returned work is still checked against the current session identity.

The Windows media session owns one unnamed high-resolution waitable timer for its bounded poll waits. It replaces `Sleep(1)` without a global timer-resolution change or busy-spin. When there is no pending readback or encoder work, it waits until the pacer's next capture deadline; pending work and immediate retries retain the short interval. Requested waits are clamped to the remaining450ms read budget; existing2s progress/pending limits remain. A separate fresh QPC comparison records actual waits; policy simulation counts are not measured CPU use, production capture or input-to-display evidence. The normal hardware-only encode path still includes GPU readback and CPU NV12 copies. Full GPU-surface encoding and asynchronous retained-sample reuse require separate ownership/capability evidence.

CI additionally requires a twelve-frame3840×2160/60fps software-MFT-to-Mac decode fixture, alongside the existing30fps4K and120-frame fixtures. This proves codec/profile interoperability and resource bounds, not sustained hardware4K60 performance.

## 4K and local typing

Quality is selected on Windows before sharing: maximum3840×2160/30fps/40Mbps by default, optional4K60/40Mbps or1080p60/20Mbps. Ready reports actual capture dimensions; capture preserves aspect and never upscales a smaller source. All producer/consumer size gates use even dimensions and the8,294,400pixel bound. Encoder in-flight count2, decoder slots3 and compressed access-unit limits remain unchanged. MFT output scratch uses a finite dimension-derived budget of two validated NV12 frames (at most24,883,200bytes at4K), distinct from actual compressed bytes. The allocation is only max(AUlimit, reported minimum), not the budget ceiling; larger reported minimums fail closed. This is a resource policy, not a guarantee for every encoder.

Mac ordinary typing uses its local input method and sends committed Unicode. Local Caps Lock language/capitalization events never become Windows Caps Lock toggles. Navigation/shortcuts remain physical with owned matching key-ups; composition is cancelled and late commits rejected on revocation/focus loss. Native fullscreen removes persistent chrome height while preserving one presenter and matching aspect-fit pointer geometry. Actual IME/fullscreen/GPU4K acceptance remains a device task.
